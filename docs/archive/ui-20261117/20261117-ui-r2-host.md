Key-size transaction source-design review: the defect is confirmed at SettingsDialog::updateRequestedKeySize (combo currentIndexChanged immediately writes Security::KeySize). It causes Cancel to retain an unaccepted setting and consumes the comparison used to enable Save. Removing that immediate-write binding/unused helper and retaining the existing Save write is within UI-003/UI-012; it does not change backend security policy.

PE recommendation for explicit Regenerate: call the existing generateCertificateAt with the already-stored certificate path and std::max(kMinimumRsaBits, selected combo bits), preserving the current write destination and minimum-RSA rule. On successful explicit regeneration, commit only the matching requested KeySize as part of that immediate action; do not commit unrelated path or other drafts. On failure, do not commit the requested size. This preserves the former explicit Regenerate outcome while making ordinary field edits transactional. It requires no TlsUtility, SecureUtils or TLS policy changes.

The initial alternative (generate selected bits but never commit them until Save) has an important consequence: Regenerate at 4096 then Cancel while stored size is 2048 leaves a certificate that unchanged isCertValid rejects, so a subsequent application start regenerates at 2048. This creates a second unexpected fingerprint change. The consistent explicit-action variant is therefore recommended; PM disposition and final tests are pending. Tests should cover ordinary combo edits without settings/certificate mutation, Reset/Cancel/Save, failure non-commit and successful regeneration metadata/certificate agreement.
